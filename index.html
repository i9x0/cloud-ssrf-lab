Server-Side Request Forgery to Cloud Metadata

An isolated, reproducible Docker lab that rebuilds the exact attack chain behind the 2019 Capital One breach — SSRF → instance metadata → stolen IAM credentials → S3 data theft — then implements and measures four cloud defences against it.

The problem

Cloud virtual machines receive a short-lived identity from a local metadata service at 169.254.169.254. Any flaw that makes the server fetch a URL of the attacker's choosing — a Server-Side Request Forgery (SSRF), OWASP Top 10 A10:2021 — can read those credentials and pivot into the cloud account. This is not theoretical: in 2019 it exposed data on 100M+ Capital One customers.

The attack chain

Using only the public web interface of a vulnerable URL-preview app, the attacker walks six steps and exfiltrates the whole customer database on the undefended baseline.

1

Recon

Use the preview feature like a normal user.

2

SSRF

Point it at the metadata service.

3

Find role

Discover the IAM role name.

4

Steal keys

Read the temporary credentials.

5

List buckets

From the attacker's own machine.

6

Exfiltrate

Download 1,000 customer records.

Four defences, one per link

No single control is enough — each defence covers a different link in the chain.

Metadata

D1 · IMDSv2 enforced

Requires a session token before serving credentials, blocking simple GET-based SSRF.

Application

D2 · SSRF input guard

Resolves the host and blocks private / link-local ranges, re-validates redirects, pins the IP.

IAM

D3 · Least privilege

The instance role may only write uploads — it cannot read the customer database.

Detection

D4 · Exfil detector

Alerts when the role key is used from any IP other than the instance itself.

Key findings

1

No single control is enough

IMDSv2 leaves internal & loopback SSRF open (9/23 still hit); least privilege doesn't stop theft, only limits the damage.

2

Fix the root cause

The SSRF guard blocked 23/23 because it addresses the server-side fetch itself, not one target.

3

Defences are complementary

D1 stops theft, D3 contains a leaked key, D4 detects misuse — together they cover the whole chain.

4

No cost to usability

100/100 legitimate requests kept working in every configuration, with ~0.1 ms median latency overhead.

Run it yourself

Clone the repo and start the whole cloud locally with Docker (details in the README).

git clone https://github.com/i9x0/cloud-ssrf-lab.git
cd cloud-ssrf-lab
python setup.py            # lab keys + synthetic data
docker compose up -d       # start the 8 services
docker compose run --rm attacker python attack_chain.py   # live attack
python run_experiment.py   # full evaluation
Safety: this lab is deliberately vulnerable and runs only inside isolated Docker networks on one machine. All customer data is synthetic; all lab credentials are random and local. Never expose it to the public Internet.
